# ExploreX security and production audit

Audit date: 2026-11-07

This is a code-level audit and regression pass, not a penetration test or a guarantee of security. Findings below distinguish implemented controls from items that still require production infrastructure or manual verification.

## Scope and findings

| Area                        | Finding and action                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication              | Clerk middleware protects application pages except the public home and sign-in/sign-up pages. API routes are intentionally public at the middleware layer and must authenticate or validate their own public access. Trip, reminder, user, AI, and admin handlers do so server-side.                                                                                       |
| IDOR                        | Trip reads, updates, deletes, duplicate operations, reminder mutations, and saved-city reads use server-derived owner predicates. Regression tests cover cross-user trip read/update/delete, reminder update/create, and saved-city reads. A composite database foreign key now requires a reminder's user to own its linked trip. Admin analytics rejects a non-admin before querying analytics. |
| Account linking             | Clerk identity is derived from the active server session. Legacy user matching by email now requires Clerk to report the primary address as verified before attaching the Clerk identity to an existing ExploreX row. |
| Retryable writes            | Trip saves deduplicate by the owner-scoped `(userId, planHash)` unique constraint. Reminder POST accepts an optional `Idempotency-Key` (maximum 128 characters), persists it per user, returns an existing result for an identical retry, and rejects reuse with a different payload. Saved-city POST is an idempotent upsert. |
| Transactions and constraints| Trip plus nested itinerary and analytics creation is transactional. Saving a city now transactionally upserts the guide and owner relation. Reminder/trip ownership is also enforced in PostgreSQL, not only by the route. A migration preflight aborts without modifying rows when existing reminder/trip ownership is inconsistent. |
| Query and mutation bounds   | JSON bodies are streamed with a 256 KB cap. Trip listing uses owner-scoped keyset pagination capped at 30; reminders are capped at 50; saved city catalog is a fixed checked-in list. Saved-city writes now use the configured trip-write rate limit and strict slug/duplicate query validation. |
| SQL and data projection     | The two raw analytics queries use static SQL with bound timestamp parameters; JSON values are guarded before numeric casts. Routes use explicit selects for private records. No request-supplied SQL identifiers or raw execution calls were found in reviewed routes. |
| Public story privacy        | Audit found that `/api/stories` returned recent trip destinations, origin, budget, dates, and account names/avatars without a consent or public-visibility model. Removed the database read; the route now serves curated destination profiles only. Added a regression test to prevent private trip data from entering this public response.                              |
| Admin authorization         | Authorization uses the persisted role or server-configured `ADMIN_USERS` allowlist. User profile synchronization does not accept a role from the request body. Admin pages are also marked noindex.                                                                                                                                                                        |
| Weather SSRF/input abuse    | The weather route now accepts only bounded coordinates or a known city, rejects duplicate/unknown query parameters, always calls the fixed Open-Meteo origin, is rate-limited, times out, validates provider output, and does not share-cache exact coordinates. Regression tests cover URL injection, invalid coordinates, malformed provider data, and timeout behavior. |
| XSS and prompt injection    | React renders user and AI text as text. AI output is schema-validated and prompt assembly treats conversation and retrieved content as untrusted. JSON-LD escapes `<` before insertion. No general HTML rendering of AI or user text was found in the audited flows.                                                                                                       |
| Redirects and outbound URLs | Sign-in and sign-up redirects go to the fixed `/` path. Weather constructs a fixed provider URL; no request-supplied URL is fetched. External source links are rendered as links with `rel="noreferrer"`; review any future user-editable outbound URL feature separately.                                                                                                 |
| Secret handling             | `.env.example` contains placeholders and documented variable purposes. `.env` is ignored and is not tracked. Server-only modules hold database/provider secrets; public variables are limited to Clerk's publishable key and the public site origin.                                                                                                                       |
| Rate limits and queues      | Production requests require Arcjet configuration; the process-local limiter is development-only. AI and travel-provider queues are bounded per process and log saturation. They are not distributed queues or deployment-wide concurrency limits.                                                                                                                          |
| Private indexing            | Added `robots.txt`, a sitemap containing only public destination/content pages, canonical metadata, Open Graph metadata, and WebSite JSON-LD. Admin, trip planning, saved trips, saved cities, and auth pages are marked noindex. Configure `NEXT_PUBLIC_APP_URL` to the actual production HTTPS origin; sitemap output is empty without it.                               |
| Database changes            | Earlier migrations add normalized trip projections and analytics indexes; the Phase 4 migration adds an optional reminder idempotency key, owner-matching composite FK, and money/currency check constraints. It preserves records and aborts on ownership or money-semantic mismatches. It has not been applied to a live or staging database in this session. See the recovery plan below before deployment. |

## Regression coverage

The Vitest suite covers pure optimization/validation/cache/rate-limit/AI parsing behavior, route-level trip and reminder ownership, reminder idempotent replay, saved-city owner scoping, verified-email account linking, non-admin analytics access, hostile/malformed weather requests, and the public stories privacy boundary. Provider failures are converted to generic responses; timeout and malformed data cases are tested without making external requests.

The route tests mock Clerk/database boundaries. They are not a substitute for integration tests against a disposable PostgreSQL database, and they do not simulate real migration drift, transaction rollback, or database outage behavior. No Playwright dependency or authenticated browser fixture is configured, so the full sign-up-to-export journey and keyboard/screen-reader/contrast behavior have not been run in a browser during this audit.

Trip sharing is not implemented. Saved trips remain private; there is no public share identifier or share route to test. Do not expose a trip through a new sharing feature without non-guessable identifiers, owner-controlled visibility, and revocation.

## Remaining risks and production recommendations

- Apply the committed Prisma migration only after the backup and staged rollout process below. The migration has not been applied or verified against a live PostgreSQL instance here.
- There is no schema-level `TripExpense`, review, discovery, or persisted AI-run model because the inspected product has no corresponding durable workflow. Do not create placeholder entities until a feature and retention/access policy require them. Static destination catalog records remain versioned data and `SiteDataset` remains a versioned JSON snapshot; these are not user-owned relational records.
- Set `DATABASE_URL`, `DIRECT_URL`, Clerk keys, `ARCJET_KEY`, and `NEXT_PUBLIC_APP_URL` in the deployment environment. Configure `OPENROUTER_API_KEY` only when AI planning is enabled and `CRON_SECRET` only for the due-reminder job. Never copy production secrets into this repository.
- Use a pooled PostgreSQL URL at runtime and monitor connection saturation. Current rate limiting is shared through Arcjet, but caches and request queues are per instance. Add a shared queue only if measured demand needs cross-instance admission or durable asynchronous work.
- Run authenticated Playwright flows with disposable user A/user B/admin accounts against a staging deployment and disposable database. Include failed transaction, duplicate, missing-row, unavailable-provider, and migration-mismatch cases.
- Manually verify WCAG 2.2 AA keyboard/focus behavior, labels, contrast, screen-reader announcements, and reduced motion at supported breakpoints. Automated checks alone do not establish conformance.
- Set a browser performance baseline for LCP, INP, and CLS on representative mobile and desktop devices. The homepage map is now deferred until near the viewport, but this repository has no field Web Vitals collector or before/after production measurements.
- Retain provider quotas and Arcjet policies appropriate for total deployed instance count. Alert on provider timeouts, queue rejection, database errors, and AI cost anomalies.

## Database semantics and recovery

- `Trip.budgetAmount` and the legacy hotel/price text fields are compatibility/display values and do not reliably express minor units. New machine calculations should use `budgetAmountMinor` / `priceAmountMinor` / `estimatedCostMinor` with the associated ISO 4217 `budgetCurrencyCode` / `currencyCode`. PostgreSQL checks require nonnegative minor-unit amounts to carry an uppercase three-letter currency code. `budgetAmountMinor` is the amount in the currency's minor unit (for example, paise for INR); never infer a currency from a formatted string. Legacy values were not rewritten by the Phase 4 migration.
- `remindAt` and audit timestamps are PostgreSQL `TIMESTAMPTZ(3)` instants. `Reminder.timeZone` stores the validated IANA zone used to interpret/display the reminder. `TripPreference.start_date` and `end_date` are calendar dates without a local time; no timezone conversion should be applied to them.
- No public/unlisted trip-sharing capability exists. Existing Web Share behavior shares a client-generated summary; it does not grant access to the persisted trip. Saved trips remain private.
- Before deployment, create and verify a restorable custom-format backup, for example `pg_dump --format=custom --file=pre-phase4.dump "$DATABASE_URL"`, and inspect it with `pg_restore --list pre-phase4.dump`. Restore to an isolated database and verify row counts and critical trip/reminder ownership before migration. Never use production credentials for a local test restore.
- Deploy first to a production-like staging copy and run `npm run db:deploy`, then validate sign-in/account linking, trip CRUD, reminder CRUD/retry, and saved-city writes. The new migration intentionally raises an exception if any existing reminder points to a trip owned by a different user. Investigate and preserve those rows before deployment; do not bypass the check or delete records to make it pass.
- Prisma migrations are forward history, not a general reversible schema transaction. If deployment fails before commit, restore the pre-migration backup or fix the data and retry. If application code has begun writing idempotency keys, rollback to old code is safe because the added column is nullable; dropping the column/index or reverting the composite FK can discard retry semantics or reopen the ownership gap. Prefer a forward fix. A full database restore loses writes made after the backup, so coordinate a write freeze or reconcile those writes before restore.
- Keep database backups encrypted, access-controlled, and under the organization's retention policy. Record backup time, database identity, migration version, and restore test outcome outside the repository; never commit backups or credentials.

The audit found and fixed the public stories privacy exposure described above. No unresolved critical vulnerability was identified in the code paths reviewed after that fix. The listed staging, migration, browser, and infrastructure checks remain required before making a production security or accessibility claim.
